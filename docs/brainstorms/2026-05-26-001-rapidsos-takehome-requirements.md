# RapidSOS Take-Home — Requirements

## Summary

Python CLI agent that takes one prompt, runs a direct-Anthropic-SDK tool-call loop (search via SearXNG → fetch → summarize) and outputs a markdown briefing. Built for **defensive readability** — every piece owned and live-extendable via Claude Code, not "production-grade" optimization. Scope target: spec-complete behavior on 4 prompts + behavior tests + 2 review rounds + 1-2 committed briefings, target ~4-5 hours of build + finalize.

## Problem Frame

The candidate is interviewing for Senior SWE II, AI Operations at RapidSOS — a 3-person internal AI-builder pod. The take-home (PDF in `docs/context/`) is a competitive & market intelligence agent. Interview is 60 min live with Martin Vejmelka (SVP, AI Product Strategy & Innovation — Prague-based, PhD nonlinear dynamics, math-rigor) and John Katt (Senior Director Product — civic-tech background, NSION first-responder experience). Live extension (20-30 min, unknown extension) is part of the format.

**Primary goal:** close the offer. **Secondary:** validate that AI Ops at scale is the candidate's next chapter.

**Operating constraint that determines every other decision:** ownership > completeness. The worst failure mode is being unable to explain *why* a piece of the code works the way it does during live coding. This is worse than imperfect implementation. Therefore: minimal-abstraction stack, behavior tests for the agent's contract, multi-round review focused on understanding, and a build process that uses Claude Code while keeping the candidate as the architect-in-the-loop.

This document captures **product requirements only**. It does NOT include defense talking points, AWS-gap framing, or pre-rehearsed answers — those scripts contradict the ownership-from-implementation posture and were deliberately removed from the prep set after a prior round of premature decision-fixing (see deleted `02-architecture-decisions.md`, `08-defense-talking-points.md`, et al.).

## Actors

- **A1 — Candidate (Slava):** Builds the artifact using Claude Code. Submits to GitHub 24h+ before interview. Defends design choices and live-extends during the 60-min interview.
- **A2 — Briefing consumer (RapidSOS internal operator):** Hypothetical Monday-morning reader — exec or strategy persona. 3 minutes to triage what happened in the public-safety-AI space. Reads markdown in a doc / Slack / email. Does not run the agent themselves.
- **A3 — Interviewers (Martin + John):** Two-axis probing — Martin on technical decisions and failure modes, John on product judgment and user-moment realism.

## Key Flows

- **F1 — Build flow.** Candidate scaffolds via Claude Code, iterates per implementation unit, runs behavior tests after each unit, commits when tests pass. Two review rounds via `/ce-code-review` (or equivalent). Real briefings generated by running the agent against the four spec prompts.
- **F2 — Operate flow.** `python -m agent "<prompt>"` → SearXNG search → fetch top sources → summarize → markdown briefing printed to stdout + saved to `data/briefings/`. Run line appended to `data/logs/runs.jsonl`.
- **F3 — Defense flow.** Live extension during interview — candidate reads own code aloud, uses Claude Code fluently to implement extension, verbalizes decisions. PDF explicitly: *"Using AI coding tools fluently is a positive signal."*

## Requirements

### Functional (spec-mandated)

- **R1 — Agent must handle four target prompts** through the same loop (no per-prompt hardcoding):
  - "Give me a briefing on everything published about RapidSOS in the last 7 days."
  - "What are the top 3 public safety AI stories from this week?"
  - "Find any press releases or news mentions of our competitors: Carbyne, RapidDeploy, Prepared."
  - "Summarize the sentiment of recent coverage of AI in emergency dispatch."

- **R2 — Tool `search`** uses SearXNG running in local Docker. Accepts query string. Returns ranked list of `{title, url, snippet}`.

- **R3 — Tool `fetch`** retrieves full text from a URL. Handles HTML stripping. Stores metadata (source domain, publish date if available, content type) alongside text.

- **R4 — Tool `summarize`** takes the original prompt and fetched documents. Returns structured markdown briefing including: **key themes**, **notable quotes/data points**, **sentiment (positive/neutral/negative — 3 classes, no finer)**.

- **R5 — CLI invocation:** single prompt as positional argument. `python -m agent "<prompt>"`.

- **R6 — Storage:** flat files only. No DB. Paths: `data/fetched/{url_hash}.json`, `data/briefings/{timestamp}-{slug}.md`, `data/logs/runs.jsonl`.

- **R7 — README** covering: how to run, what it does, key design decisions and tradeoffs. **3 sections per PDF spec — no more.**

- **R8 — GitHub submission** to `mcho@rapidsos.com` 24h+ before interview.

### Ownership / defensibility (Slava's bar)

- **R9 — Every implementation file** must be readable end-to-end in one sitting by the candidate. No clever abstractions. Boring > clever.

- **R10 — Behavior tests** on the agent's output contract. One test per spec prompt: assert the briefing has TL;DR, key themes (≥1), sources (≥1), sentiment in `{positive, neutral, negative}` enum. Schema-shape validation only — NOT content correctness.

- **R11 — Two code review rounds** before submission. Round 1: correctness + simplicity. Round 2: scope-guardian + adversarial.

- **R12 — 1-2 committed briefings** in `data/briefings/` — real runs against the spec prompts, committed as-is including honest limitations. NOT hand-curated or polished.

- **R13 — Graceful failure paths** on network errors (one retry), LLM rate limits (exponential backoff, max 3 retries), malformed HTML (fallback to raw extraction), empty search results (return "no results" briefing, don't crash).

## Acceptance Examples

- **AE1 — RapidSOS 7-day prompt** produces a markdown briefing with ≥3 sources, citations, sentiment label, TL;DR. Surfaces at least one of: AT&T ESInet launch (Apr 29 2026), Renner documentary, recent RapidSOS blog post.

- **AE2 — Competitor prompt** produces a briefing that surfaces parent companies — "Carbyne (Axon)", "Prepared (Axon)", "RapidDeploy (Motorola)". This is a small product-judgment requirement on the summarize prompt; tests assert format.

- **AE3 — Sentiment prompt** produces a briefing with sentiment-class verdict + ≥3 sources backing the verdict.

- **AE4 — Empty / weak search results** returns a "no useful sources found" briefing structure rather than crashing.

- **AE5 — Behavior tests** all pass green before submission.

- **AE6 — Cold-run test:** `docker compose up -d && python -m agent "<any spec prompt>"` works in under 2 minutes on a fresh checkout with only `ANTHROPIC_API_KEY` in `.env`.

## Key Decisions

- **D1 — Python over TypeScript.** Reasoning: candidate is directing Claude Code rather than hand-writing; Python has stronger AI-agent corpus, simpler pytest ergonomics, and Anthropic SDK is Python-first. JD names LangChain/LlamaIndex as nice-to-have. The candidate's read fluency in Python is sufficient for the role of architect-in-the-loop.

- **D2 — Direct Anthropic SDK over LangGraph or LangChain.** Reasoning: 3 tools + single-turn loop = framework overhead exceeds value. The agent loop is ~150 lines and fully owned. Live extension is faster without framework gymnastics. The candidate has shipped LangGraph in production (Aibility) — choosing not to use it is the judgment signal, not unfamiliarity.

- **D3 — Single Claude Sonnet, no Haiku/Sonnet split.** Reasoning: a two-model split adds wiring overhead, requires defending an unmeasured cost claim, and contradicts "single mental model to defend." Sonnet for all calls (tool orchestration + summarization). If cost-discipline is ever asked, the honest answer is: "I deliberately did not split — for 3h scope, one model = one defense surface."

- **D4 — Markdown output, not JSON.** Reasoning: PDF prompts ("briefing", "top 3 stories") are operator language. Consumer is a human reading in Slack/email. A `--format json` flag is a 10-line live-extension if needed.

- **D5 — Behavior tests, not unit-coverage tests.** Reasoning: one test per spec prompt asserts the briefing shape (TL;DR present, themes ≥1, sources ≥1, sentiment ∈ enum). Validates the actual contract. Padding with unit tests for parsing internals would be coverage theater contradicting "ownership > completeness."

- **D6 — Flat-file storage with `runs.jsonl` observability.** Spec mandates no DB. `data/fetched/` doubles as within-run cache. `runs.jsonl` is one line per run (prompt, tools called, errors, latency) — greppable, post-hoc analyzable. Explicit alternative to a vendor (Langfuse) is acknowledged in Scope Boundaries.

- **D7 — Iteration cap at 8 with first-principles justification.** Reasoning: a sensible loop has 3 logical phases (search, fetch a handful, summarize) → 6-8 tool calls is the ceiling of what's reasonable. The cap is a kill switch, not a design target. NOT cited as "Aibility data" — that would be unverifiable claim. If a run hits the cap, runs.jsonl marks status as partial.

- **D8 — Defense emerges from ownership, not from pre-rehearsed scripts.** Reasoning: ventriloquized 60-sec answers (the deleted `08-defense-talking-points.md` approach) put words in the candidate's mouth he didn't author and would falsify under follow-up. The defense voice for hard live questions (Aimee transfer, AWS gap, domain humility) emerges from understanding the code + honest calibration of what the candidate knows vs doesn't. Not a requirement of this doc; an explicit non-deliverable.

- **D9 — Scope target = C with fallback ladder.** Spec + ownership: 4 prompts working, behavior tests, 2 review rounds, 1-2 briefings. If time pressure hits during build, the cut order is committed NOW: (i) cut 4th prompt (sentiment) first, (ii) cut 2nd review round, (iii) cut 2nd briefing. Hard floor: 3 tools work + 1 briefing + 3 behavior tests + README. Mid-build decisions are pre-made.

## Scope Boundaries

### Deferred for later (named v2 items)

These would matter at production scale but are deliberately out of this 3-hour CLI scope. Surface them in conversation if asked "what would v2 look like":

- **Langfuse / observability vendor hook** — candidate's Aimee muscle-memory item. Explicit v2.
- **Eval harness with labeled set** — for sentiment calibration (Cohen's kappa) or briefing-quality scoring. Explicit v2.
- **Scheduled runs + Slack delivery** — where the briefing becomes habit-forming for an internal team.
- **Cross-run dedup + source clustering** — same press release shouldn't generate two themes across two runs.
- **Source reliability scoring** — weight TechCrunch differently from SEO farms.
- **Sentiment trending over time** — not just per-run; "sentiment trended positive over 4 weeks."
- **Operator feedback loop** — thumbs-up/down per briefing → prompt tuning.

### Universal anti-patterns excluded

Standard "what I deliberately left out" list — confirm if asked:

- **RAG / vector DB** — flat files sufficient at this volume.
- **Multi-agent architecture** — single agent with 3 tools is enough.
- **Per-prompt-type routing** — all 4 prompts route through same loop.
- **LLM-as-judge** — would add a second eval step requiring its own justification.
- **Pretty UI / web frontend** — out of spec.
- **Deployment** — spec says local only.
- **Two-model split (Haiku + Sonnet)** — explicitly chose not to; see D3.

### Outside this document's responsibility

- **Defense talking points / interview scripts.** See D8. The doc captures product decisions; the interview is unscripted.
- **Interviewer profiles, panel question banks, AWS-gap framings.** These live in `docs/99-research-inputs.md` as INPUTS to candidate's own thinking — not commitments embedded in the artifact.

## Dependencies & Assumptions

- **Docker** for SearXNG local instance.
- **Python 3.11+** and `pip install -r requirements.txt`.
- **`ANTHROPIC_API_KEY`** in `.env`.
- **Claude Code** (or equivalent AI coding agent) available during live coding session.
- **Assumption to verify in build start (first 30 min):** SearXNG returns usable results on RapidSOS-related queries with recent date qualifiers. If not, the cold-start risk is real — fallback is to acknowledge limitation in README and proceed with whatever SearXNG produces honestly (NOT hand-curate briefings).
- **Assumption:** the 4 spec prompts produce behaviorally-distinguishable briefings via the same loop. If one prompt consistently produces a weak briefing under the standard loop, that is a finding worth documenting in README "Limitations," not a reason to add per-prompt routing.
